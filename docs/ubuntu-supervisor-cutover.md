# Ubuntu cutover with Cron and Supervisor

Use this profile with the existing Ubuntu release operations guide. Keep hostnames, database option files, service inventory, artifacts and acceptance results in the operator's private records. The example release root is a proposal. All installation, service and cutover commands below require site approval.

## Read-only preflight

Run from a separate, reviewed checkout as the deploy user. Set LEGACY, ROOT and LEGACY_SHA to the inspected checkout, proposed sibling root and full approved baseline. Have the DBA provide a mode 0600 MySQL client option file owned by that user, with a SELECT-only account and the verified application database in its [client] section. Confirm the effective queue and failed-job connections point at that database and use jobs and failed_jobs. Adapt the aggregate query privately for custom mappings.

```bash
bash deploy/ubuntu-preflight.sh "$LEGACY" "$ROOT" "$LEGACY_SHA" "$HOME/.medsurvey-inspection.cnf"
```

The inspection compares the live BackupService to the original Git blob, checks PHP/FPM, storage identity, installed units and active maintenance, and prints aggregate queue counts. With the file driver, a runtime cleanup invoked after Artisan down that removes the down file cancels maintenance before the intended up. The release controller checks the result of Artisan down and the shared marker before and after migrations. Its independent Nginx gate stays closed through cache building, private readiness and consumer restart. The lost_maintenance regression simulates marker loss and verifies the public gate stays closed.

For an already inventoried host, use the [focused field command and isolated restore drill](ubuntu-field-acceptance.md).

Review system and user timers, cron for each service account, Supervisor includes, containers, other hosts with database access, the effective cached broadcaster destination, DNS and the tunnel origin privately. Verify the peer that actually terminates the WebSocket and owns the queue. A zero local process count is inconclusive. Repeat aggregate measurements across a representative interval, including a known submission. The oldest timestamp is UTC Unix seconds. Keep delayed and reserved jobs in the count. Retain the old queues and failed rows for a separately approved review.

## Choose the service profile

Both public and authenticated submissions dispatch SurveySubmitted after saving. It broadcasts the response ID on private system, facility and department channels. API retries with the same client response ID return the saved response. Delivery can repeat after a process dies between sending and acknowledging. Consumers should deduplicate by response ID. The repository has an optional Echo connection and no production listener for this event. Confirm any separately deployed dashboard or integration. Archive, backup and prune execute as scheduled commands. Mobile offline submission uses its own retry storage.

* For approved local delivery, prove the proposed queue is empty, confirm the producer can be redirected, set DB_QUEUE=medsurvey-live and DB_QUEUE_RETRY_AFTER=90 in the private environment under the gate and rebuild cached config. Never point the new worker at the historic default queue. Stop or coordinate every previous consumer. Install just the approved Supervisor stanzas. One worker is a conservative pilot, pending job arrival rate, service time, age and CPU measurements. Keep timeout 60 s, tries 3, backoff 10 s and stopwaitsecs 85 s. Confirm pcntl is loaded in PHP CLI. Benchmark peak arrival rate versus completions and adjust the Supervisor programs and hook checks together before scaling.
* If no consumer requires broadcasting, approve BROADCAST_CONNECTION=null and VITE_ENABLE_BROADCASTING=false for the candidate. New submissions then skip queueing this broadcast. Pending records stay untouched. The bootstrap uses the original code until the candidate is deployed. Select disabled for each verified unused role. An external service requires its own approved drain, readiness and release-coordination adapter.
* For local Reverb set REVERB_HOST and REVERB_SERVER_HOST to 127.0.0.1, both ports to 8080 and REVERB_SCHEME=http. Preserve the existing application ID, key and secret. Configure REVERB_ALLOWED_ORIGINS with exact browser hostnames (comma separated, no schemes, ports or wildcard). The reviewed optional browser build uses a reachable TLS hostname, VITE_REVERB_PORT=443 and VITE_REVERB_SCHEME=https, with only the public app key. Resolve that hostname internally for LAN. Keep /apps/ publishing internal. Verify an allowed origin succeeds, an unrelated origin fails and reconnection succeeds after restart. Keep Cloudflare routing changes under separate approval.
* Supervisor autostart is disabled for initial installation. After backlog review, an operator starts Reverb then the worker behind the gate. Unexpected exits restart automatically. After host reboot, keep traffic closed until those approved programs are started and verified, or approve a separate boot policy. Do not use supervisorctl start all or retry/clear all jobs. Before reopening validate the real WebSocket handshake and a new-queue fixture against the approved environment.

## Provision and verify

For an enabled browser connection export VITE_ENABLE_BROADCASTING and the public VITE_REVERB_APP_KEY, HOST, PORT and SCHEME fields in the shortcut's private site.conf using their full VITE_REVERB_ names. The release build runs before the shared .env is linked.

Install ubuntu/check-consumer.php beside consumers.sh, root-owned and readable by the deployment user. The hook checks the configured queue and retry window before starting the worker. For local Reverb it requires an explicit origin allowlist and a successful signed query against a fixed, empty readiness channel. During the initial layout switch, keep any currently unused roles disabled. Enable new roles in a separate approved, gated step on the candidate after its configuration supports these checks. Always rebuild the candidate's config cache after changing private environment values. A change to VITE settings also requires a fresh approved frontend build.

1. Reserve capacity on each backing filesystem for the unpacked release, npm/vendor build, uncompressed SQL staging, uploads archive, failed deployments and retention. Confirm the nominated root is outside both document roots and the legacy tree. Create a new deployment-owned ROOT, shared and releases with the web group and mode 2750. Create ROOT/recovery as deployment owner mode 0700. Clone the read-only repository into ROOT/repo as deploy user. Verify both full SHAs resolve. Keep control paths, their parents, repository, lock, approved-commit and hooks inaccessible for web writes. Place the deployment command and privileged helpers under root-owned /usr/local/lib/medsurvey. Keep the legacy command and vhost privately backed up.
2. Repair excessive legacy rights before executing legacy PHP as the deployment user. Inspect ACLs and parent directories with namei and getfacl. Code, public and bootstrap/cache directories should be owner-writable, web-readable/traversable (0750 or 2750). Files should normally be 0640 with executable bits retained where needed. Protect bootstrap/cache/config.php like .env (0640). Inspect copied vendor and assets for unsafe symlinks or unexpected local edits. Shared .env remains deployment-owned and group-readable. Grant write only on needed runtime paths under storage (including logs, sessions, views, cache data and designated uploads/backup destination). Use narrowly scoped default ACLs on those directories for both deploy and www-data so newly created files stay mutually writable when required. Check cache manifests exist before serving a read-only release. Validate access as both identities, including creating and removing a synthetic runtime file in rehearsal. Verify www-data cannot write public, release source, config cache, gate, hooks or their parents and cannot traverse recovery. Restrict backup readers to the backup operator and any explicitly required application identity. Keep MySQL data in place.
3. Install the six hook files per the [release operations guide](ubuntu-release-operations.md). Install ubuntu/consumers.sh, check-consumer-cwd.sh, drain.sh, schedule.sh, nginx-traffic.sh and the pinned controller as root-owned executable files under /usr/local/lib/medsurvey. Install identical, reviewed root-owned site.conf copies in /etc/medsurvey-deploy, ROOT/hooks and /usr/local/lib/medsurvey (0640, deploy-readable). Start with ubuntu/site.conf.example, replace all examples privately and set the measured MIN_FREE_KIB. Pin PHP CLI to 8.2 on the deployment and cron PATH. Verify composer runs under that PHP. Use visudo to grant the deployment user only /usr/bin/systemctl reload php8.2-fpm.service and reload nginx.service, /usr/bin/supervisorctl status/start/stop followed by each literal approved program name, and /usr/local/lib/medsurvey/check-consumer-cwd.sh followed by each literal approved program name. Use separate exact command entries, NOPASSWD, no wildcard and no shell. Confirm resolving a worker PID's cwd matches current under the helper.
4. Integrate ubuntu/nginx-public.inc.example into **every** serving vhost and ubuntu/nginx-private.conf.example as a separate loopback server. Merge existing TLS and application-specific directives, remove conflicting locations, require an exact public hostname and reject unknown hosts on public listeners. Leave the private port outside all Cloudflare ingress rules. Configure pm.status_path and the separate pm.status_listen socket in the target pool. Verify the status response describes the serving pool and reports zero active processes when idle. A graceful Nginx reload retires requests buffered ahead of FPM. Verify it is acceptable on this host. Established long-lived sockets can hold the old generation open. Close clients during the window and keep the gate closed if drain times out. The deployment waits for the retired workers and an idle FPM queue. Do not use a forced worker timeout as proof of a graceful drain. Run nginx -t and the FPM configuration test privately before reload. During layout adoption install the gate in the **old** vhost first, with its original root. Verify all public and LAN probes receive the marker and a private health check reaches the expected release. These vhost snippets assume requests can reach the origin directly only through the approved LAN and tunnel paths.
5. Keep HTTPS at the public edge. Trust only the immediate proxy IPs. Use distinct Nginx listeners for tunnel and direct LAN if necessary, sanitize incoming forwarding headers at the trusted boundary and verify the REMOTE_ADDR FPM actually sees. The public HTTPS vhost must reject/redirect plain public HTTP. Keep cookies host-only, HttpOnly and SameSite=Lax. The app protects cookies on effective HTTPS after proxy handling. A separately named direct HTTP LAN IP can retain its existing session policy while clients migrate to split DNS and a trusted internal TLS certificate. Once all entry paths use HTTPS approve SESSION_SECURE_COOKIE=true. Test public login, redirect, logout and account switching on both routes, with the same APK against the approved HTTPS API. Confirm an untrusted LAN peer cannot assert its own HTTPS status.
6. Keep one per-minute cron entry under the deployment account. At the gate, back up its crontab, remove only the legacy schedule entry, wait for existing schedule:run and any child archive, backup or prune commands to finish, then replace it with the line below. Verify no second systemd, Supervisor or cron runner exists. Provision scheduler.lock writable by the deployment account only. The wrapper holds an exclusive lock for the entire foreground run, resolves current after acquiring it, and skips closed/paused periods. Pause waits for that lock; global cron keeps running. Check schedule:list in Asia/Riyadh against 00:00 prune, 02:30 archive (3 years) and 03:00 backup, or the site's verified stored overrides. Review missed runs after a maintenance window. Alert on a missing scheduler.success log per expected job after its completion window. This marker is emitted by the candidate's successful command callback. Keep cron errors in private operator mail or monitored logs.

```cron
* * * * * /usr/local/lib/medsurvey/schedule.sh
```

## Approval, transition and rollback

Freeze legacy deployments and all writers. Close and drain each ingress, enter legacy file maintenance via /usr/bin/php8.2 artisan down from LEGACY, and drain schedulers and consumers. Verify a restorable, encrypted independent copy of SQL, public/private uploads, environment and service config. Install the six hooks and adapters **before** the window; test their contracts on a disposable host. Keep the old path intact throughout. The following command prepares the layout on the **old** SHA only.

```bash
bash deploy/adopt-legacy.sh "$ROOT" "$LEGACY" "$LEGACY_SHA"
```

While gated, switch vhosts to current/public, reload the verified FPM service, run artisan up on the bootstrap, check private health, authenticate fixtures, resume the approved consumers through the hook and open all entrances last. For a layout failure preserve the gate, restore the old vhost, cron and consumer working paths, reload, bring the legacy app up, verify a private database-backed request, then resume and reopen. Preserve shared links to original storage and .env.

Install the pinned deploy-shortcut.sh as /usr/local/bin/deploy-medsurvey. Write the separately approved **full candidate SHA** plus newline to a private temporary file in ROOT and atomically rename it to approved-commit. Confirm type -a deploy-medsurvey. Run the following under the deployment account.

```bash
deploy-medsurvey
```

For a failed code deployment, preserve the private recovery record. Follow the locked [release rollback procedure](ubuntu-release-operations.md#deploy-and-recover), including fresh private readiness, service cwd and public checks. After a migration, confirm schema compatibility before switching code. Require a separate approval and isolated restore rehearsal for any SQL/uploads restore.

## Backup evidence and acceptance

The scheduled backup command creates and verifies **SQL**. Deployment also archives public and private uploads. Before adoption provide an independent scheduled encrypted off-host copy covering uploads and SQL at a consistent recovery point, plus protected environment and service definitions. For example, use the operator's backup agent with an append-only remote repository and separately escrowed recovery credentials. Quiesce writes or use coordinated database and filesystem snapshots. Record UTC completion time, file count, sizes, checksums, retention and verification outcome privately. Alert on stale or failed runs. Rehearse decrypting to an isolated network, importing into a new empty MySQL schema and comparing file hashes, tenant row counts and application fixture reads. Disable delivery services in the restore environment. A VMware snapshot alone shares the host failure domain. Use the existing retention guide and the site's approved RPO/RTO. Preserve existing backups and suspend pruning of any copy needed for the transition.

Use the [physical Android checklist](ubuntu-release-operations.md#android-acceptance). Also check logout in a second tab and login as a different tenant following WebSocket reconnect; verify the old account receives no private events and cannot authorize the previous channel. Existing Echo initialization has no shipped survey subscriber. A separate subscriber needs its own logout, disconnect and account-switch test.

Keep tool upgrades in a separate window. Node 20 has reached EOL; CI exercises the lockfile on Node 22 and 24 LTS and the browser/PWA suite on 24. PHP 8.2 and 8.3 are in security support through the end of 2026 and 2027 respectively. Rehearse a PHP minor upgrade with matching CLI, FPM socket, extensions and controller before switching. Stage the latest stable Composer 2 PHAR, verify its published digest/signature, run validate, install from the unchanged lock, check-platform-reqs and audit under the target PHP; retain the old binary for rollback. Record exact tested versions privately.
